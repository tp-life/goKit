# Polymarket 尾盘扫尾巴策略设计说明

## 1. 文档目的

本文档用于定义“尾盘扫尾巴策略”的设计方案，供后续编码实施、策略复盘和风控评审使用。

本文档描述的是**未来计划实现的策略设计**，不是当前仓库已经生效的行为。后续编码应以本文档为指引，逐项落地并补充测试。

## 2. 策略定位

### 2.1 定义

“尾盘扫尾巴策略”是指在市场结束前最后一小段时间内，专门捕捉：

- 外部参考价方向已经非常明确
- Polymarket 盘口尚未完全收敛
- 仍然存在可执行的残余定价偏差

的一类尾盘短时策略。

### 2.2 与主策略的关系

该策略不是当前主入场策略的附属条件，而应作为**独立策略桶**存在。

原因：

- 主策略是提前量策略，偏向 `180s / 120s / 90s` 的提前观察与入场
- 尾盘扫尾巴是微结构策略，偏向 `20s` 以内的残差捕捉
- 二者在执行方式、成交质量、费用敏感性和风控需求上明显不同

因此，本策略必须在统计、风控、展示和自动停用逻辑上，与主策略隔离。

## 3. 设计目标

### 3.1 目标

- 在最后若干秒发现高置信度残余机会
- 以小仓位补充主策略的收益来源
- 直接持有到结算，不额外追求中途止盈
- 在不显著放大总风险的前提下，提高整体净收益

### 3.2 非目标

- 不追求提高总体成交次数
- 不追求覆盖所有市场与所有周期
- 不作为主盈利来源
- 不与主策略共享同一组判断条件和收益桶

## 4. 初始适用范围

第一阶段仅建议启用：

- `BTC:15m`
- `ETH:15m`

第一阶段不建议启用：

- `SOL:5m`

原因：

- `BTC:15m` 和 `ETH:15m` 的尾盘盘口结构相对稳定
- `SOL:5m` 噪音更强、盘口更薄、穿价与滑点更重，不适合作为第一阶段实验场

## 5. 触发时机

### 5.1 窗口定义

建议第一阶段固定为：

- `remaining <= 20s`

不建议第一阶段直接放宽到：

- `30s`
- `10s`

原因：

- `30s` 容易和当前“尾盘强信号暂缓止损”逻辑重叠
- `10s` 对延迟和盘口变动过于敏感

### 5.2 进入前置条件

仅当以下条件同时满足时，才允许评估尾盘扫尾巴：

- 当前存在活跃市场
- 当前市场属于允许启用尾盘策略的市场白名单
- 剩余时间 `<= TAIL_SWEEP_FINAL_SEC`
- 当前没有持仓
- 当前没有挂单
- 当前未被全局风控阻断
- 当前未处于尾盘策略冷却期

## 6. 信号定义

### 6.1 主信号

方向继续沿用当前主策略的核心差值定义：

`diff = chainlink_price - ptb_price`

方向定义：

- `diff > 0`：候选方向为 `UP`
- `diff < 0`：候选方向为 `DOWN`

### 6.2 强信号门槛

尾盘策略不应复用主策略门槛，而应要求更强信号。

建议第一阶段使用：

- `abs(diff_bps) >= max(TAIL_SWEEP_MIN_DIFF_BPS, base_condition_diff_bps * 1.8)`

默认推荐：

- `TAIL_SWEEP_MIN_DIFF_BPS = 9`

### 6.3 Binance 方向确认

建议第一阶段必须开启 Binance 同向确认。

要求：

- Binance 与 `Chainlink - PTB` 推导出的方向一致
- 若 Binance 与 Chainlink 偏差过大，则直接否决本次尾盘入场

### 6.4 数据实时性

尾盘策略的数据延迟要求必须比主策略更严格。

建议第一阶段使用：

- `TAIL_SWEEP_MAX_LAG_SEC = 0.8`

适用对象：

- Chainlink 最新价格时间
- Binance 最新价格时间
- 对应方向盘口更新时间

## 7. 盘口与价格过滤

### 7.1 概率区间

尾盘策略不建议覆盖极端概率区间。

建议第一阶段使用：

- `TAIL_SWEEP_MIN_PROB = 0.84`
- `TAIL_SWEEP_MAX_PROB = 0.94`

其中 `TAIL_SWEEP_MAX_PROB` 同时作为尾盘入场价格的**硬上限**。

也就是说：

- 当候选方向价格 `> 0.94` 时，尾盘策略一律不得开仓
- 不允许因为 diff 足够强、Binance 已确认，就在 `0.95+` 区间继续追价
- 后续编码时应把该限制放在尾盘策略的显式校验里，而不是只作为注释存在

原因：

- 太低的概率区间信号噪音更大
- 太高的概率区间容易变成“追最后一跳”，费用与滑点吞噬边际

### 7.2 尾盘价格上限的设计说明

尾盘策略的价格上限建议固定为：

- `0.94`

设计理由：

- `0.95+` 区间往往已经非常接近最终结算预期，剩余可赚空间显著压缩
- 在该区间继续追价，对 spread、fee、瞬时回摆和执行延迟都更敏感
- 即使胜率较高，也很容易出现“理论正确，但净收益不足”的情况

因此，第一阶段应明确采用：

- `尾盘价格上限 = 0.94`

若未来要上调，只建议在独立复盘后按小步方式评估，例如：

- `0.94 -> 0.945 -> 0.95`

不建议在第一阶段直接放宽到 `0.96+`。

### 7.3 盘口宽度过滤

尾盘策略必须过滤过宽盘口。

建议第一阶段增加：

- `ask - bid <= TAIL_SWEEP_MAX_SPREAD`

默认推荐：

- `TAIL_SWEEP_MAX_SPREAD = 0.02`

### 7.4 成交方式

尾盘策略第一阶段**不建议优先走 post-only**。

建议：

- 直接走普通限价单
- 价格贴近当前可成交价
- 如需 maker 版本，应在第二阶段单独试验

原因：

- 尾盘盘口变化快，maker 更容易出现穿价被拒
- 尾盘机会持续时间短，maker 等待会显著降低成交率

## 8. 仓位与风险预算

### 8.1 仓位原则

尾盘策略必须使用独立且更小的风险预算。

建议：

- `tail_sweep_trade_amount = base_trade_amount * TAIL_SWEEP_SIZE_RATIO`

默认推荐：

- `TAIL_SWEEP_SIZE_RATIO = 0.4`

例如：

- 若主策略基础仓位为 `5 USDC`
- 则尾盘策略目标仓位为 `2 USDC`

### 8.2 最小份额限制

由于 Polymarket 通常要求买入至少 `5 shares`，实现时不能直接写死尾盘仓位金额。

应采用：

- `最终金额 = max(目标金额, price * 5 shares)`

并在金额超过全局风控许可时放弃本次下单。

### 8.3 风险限制

尾盘策略必须额外受以下限制：

- 与主策略共用全局最大持仓市场数
- 与主策略共用全局总敞口上限
- 不允许在已有仓位时再次尾盘开仓
- 不允许与同市场主策略同时挂单

## 9. 持仓与退出规则

### 9.1 默认退出方式

尾盘策略第一阶段默认：

- 开仓后直接持有到结算

不单独挂止盈单。

### 9.2 止损策略

第一阶段不建议复用常规止损。

建议仅保留“紧急退出”条件：

- 外部信号方向在尾盘窗口内发生明显反转
- 数据延迟超过尾盘上限
- 盘口严重失真，已无法支持原判断

换言之：

- 尾盘策略是“高门槛入场，默认拿到结算”
- 不是“再套一层常规止盈止损”

## 10. 独立收益桶与停用逻辑

### 10.1 独立策略键

尾盘策略必须生成独立的 `strategyKey`，不得与主策略复用。

建议命名模式：

- `market_key|tail-sweep|20s|UP`
- `market_key|tail-sweep|20s|DOWN`

### 10.2 独立统计项

至少应单独统计：

- 成交次数
- 胜率
- 平均净收益
- 总净收益
- 平均入场边际
- 穿价率
- 下单被拒率
- 每次成交实际持有时长

### 10.3 自动停用

建议第一阶段增加独立停用条件：

- 连续亏损 `>= 2` 笔，尾盘策略进入当日冷却
- 最近 `4` 笔尾盘策略总收益 `< 0`，自动停用
- 最近 `4` 笔尾盘策略总收益 `< TAIL_SWEEP_DISABLE_MIN_TOTAL_PNL`，自动停用

默认推荐：

- `TAIL_SWEEP_LOSS_STREAK_LIMIT = 2`
- `TAIL_SWEEP_DISABLE_LOOKBACK_TRADES = 4`
- `TAIL_SWEEP_DISABLE_MIN_TOTAL_PNL = -0.5`

## 11. 与主策略的冲突规则

### 11.1 冲突原则

尾盘策略必须服从以下冲突顺序：

1. 全局风控
2. 现有持仓 / 挂单
3. 主策略已触发但未完成
4. 尾盘策略自身条件

### 11.2 具体规则

- 若当前已有持仓，则尾盘策略直接跳过
- 若当前已有挂单，则尾盘策略直接跳过
- 若主策略已在同市场生成待成交挂单，则尾盘策略不得重复下单
- 若尾盘策略已触发，则同市场本轮不得再次触发第二次尾盘策略

## 12. 配置设计建议

建议新增以下配置项：

```env
TAIL_SWEEP_ENABLED=true
TAIL_SWEEP_MARKETS=BTC:15m,ETH:15m
TAIL_SWEEP_FINAL_SEC=20
TAIL_SWEEP_MIN_DIFF_BPS=9
TAIL_SWEEP_MIN_PROB=0.84
TAIL_SWEEP_MAX_PROB=0.94
# 等价于尾盘入场价格硬上限；实现时不得允许超过 0.94 的尾盘追价。
TAIL_SWEEP_MAX_PRICE=0.94
TAIL_SWEEP_REQUIRE_BINANCE_ALIGNMENT=true
TAIL_SWEEP_MAX_LAG_SEC=0.8
TAIL_SWEEP_MAX_SPREAD=0.02
TAIL_SWEEP_SIZE_RATIO=0.4
TAIL_SWEEP_MAX_TRADES_PER_HOUR=2
TAIL_SWEEP_LOSS_STREAK_LIMIT=2
TAIL_SWEEP_DISABLE_LOOKBACK_TRADES=4
TAIL_SWEEP_DISABLE_MIN_TOTAL_PNL=-0.5
TAIL_SWEEP_HOLD_TO_SETTLEMENT=true
```

## 13. TUI / 观测要求

尾盘策略上线时，TUI 至少应新增：

- 当前尾盘策略是否启用
- 当前市场是否在尾盘策略白名单内
- 当前是否进入尾盘扫描窗口
- 当前实际 `diff_bps`
- 尾盘策略阈值
- 当前是否被 Binance 否决
- 当前是否被盘口宽度过滤
- 当前是否被全局风控拦截
- 尾盘策略最近若干笔收益摘要

## 14. 编码分阶段建议

### 14.1 第一阶段

仅实现：

- 独立配置解析
- 独立触发判断
- 独立仓位预算
- 直接持有到结算
- 独立收益桶与停用逻辑

### 14.2 第二阶段

再评估是否增加：

- maker 版本尾盘挂单
- 更精细的盘口深度过滤
- 分市场单独阈值
- 基于收益表现的尾盘仓位动态缩放

## 15. 验收标准

第一阶段上线后，至少满足：

- 能独立开关尾盘策略
- 不影响主策略已有行为
- 不与已有持仓/挂单冲突
- 尾盘策略单独可见、可统计、可停用
- TUI 可展示尾盘策略当前状态和最近收益
- 所有新增状态机均有单元测试覆盖

## 16. 当前结论

结论如下：

- 该策略具备实现可行性
- 但必须作为独立策略桶落地
- 第一阶段只建议在 `BTC:15m` 与 `ETH:15m` 上启用
- 第一阶段应采用小仓位、强门槛、持有到结算的保守版本
- 后续编码必须以本文档为实施基线，不建议直接将该策略混入现有主策略条件中
